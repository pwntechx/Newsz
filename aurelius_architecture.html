◈ Aurelius Network — Architecture Guide v1.0

Read this before touching any code. It describes how the system works, why it is structured the way it is, and how to navigate it safely.

Pipeline Order

The network runs as a sequential pipeline. Each node produces output that the next node reads. Do not run nodes out of order.

0Oracle (Aurelius) — detects sovereign signals, writes oracle_bridge_YYYY-MM-DD.json
1Bridge — structures signals, writes enriched bridge JSON
2Observer — monitors ladder watch, alerts on L-level proximity
3Walk — enriches geometry, writes walk fields to sovereign index
4Witness — audits all prior nodes, writes witness_sovereign_index.json
5Future — applies TF1 clearance filter, writes forecast_clearance_YYYY-MM-DD.json
6Witness (silent) — clearance-only pass, no interactive output
7Sim — three competing nodes (DeepSeek, Gemini, Claude) + Alchemist run positions
8Render — produces HTML dashboard from all prior outputs
◈ Entry point: Lattice (0racle_Lattice.py) orchestrates the pipeline. Do not run individual nodes manually unless debugging a specific chamber.

Core Principles

E=1 Total Preservation

No node is extracted from the system. Capital is preserved before aggression. Data once correctly written is never overwritten. The system refuses to act on void information.

Where to see it in code:

  • PRESERVE set in Lattice _cleanup_old_artifacts — lists files that are never deleted
  • ohlcv_write first-writer-wins rule — once a payload is cached, no node overwrites it
  • if data is None: return None — entry gates block on missing price data
  • return LAST_MACRO fallback — holds prior macro state rather than fabricating new state

Glass Box

Every open node is named. Every correction is shown. Nothing is hidden.

  • Chamber meta notes describe what the chamber decided, not how to modify it
  • Version notes in meta (v6.8, v4.0, PATCH_D) record what changed and why
  • Corrections shown in meta notes rather than hidden

Role Separation

Each node owns one responsibility and stays in it. Aurelius detects. Bridge structures. Walk enriches. Witness audits. Future projects. Sim acts. Render presents. Lattice orchestrates.

⚠ If you find yourself writing logic in the wrong node — Sim code that reads bridge data to make a detection decision, or Aurelius code that acts on sim positions — stop. The logic belongs in the node that owns that responsibility.

No Guess Principle

The system never assumes. It never coerces None to 0.5. It never fabricates a price. It never continues with partial data when the full data is required.

  • fetch_price returning None blocks sim entry entirely — verified in 0racle_Sim.py
  • return LAST_MACRO fallback — holds prior macro state rather than fabricating new state — verified in 0racle_Aurelius.py
  • if data is None: return None pattern — present in every fetch function across pipeline

How to Read Chambers

Each script is divided into numbered chambers. Every chamber owns one concern. Read chambers in order — earlier chambers define the ground that later chambers stand on.

Chamber 0 rule: Always imports and configuration. It is the ground. Do not move logic into Chamber 0.
Chamber last rule: Always the entry point or output. Chamber 14 in Aurelius is where the full pipeline fires. Chamber 12 is the interactive terminal.
Sub-chambers: When a concern splits — same logical position, different mechanism — chambers split into A, B, C. Example: Chamber 4.A is HTTP core, 4.A.1 is OHLCV cache, 4.B is macro audit. The number preserves position. The letter preserves separation.

Meta Notes

What they are: The comment block at the top of each chamber. They record what the chamber decided and what changed between versions.

How to read them: Read the meta note before reading the code. It tells you the intent. The code tells you the implementation. If they conflict, the meta note describes the design intent — the code may have drifted.

⚠ Meta notes are not instructions for how to modify the chamber. They are a forensic record of what the chamber is and why.

Key Files

oracle_bridge_YYYY-MM-DD.json
Primary data contract. Written by Aurelius Chamber 11. Read by Bridge, Walk, Witness, Observer, Future, Render, Sim. Contains scored signals, ladder coordinates, VSD classifications.
witness_sovereign_index.json
The network's accumulated memory. Written by Witness. Read by Sim, Walk, Future, Observer. Contains walk geometry tiers, backtest results, soul states, SAGE performance scores.
oracle_sim_state.json
Live sim positions and closed position ledger. Written and read by Sim. Read by Alchemist for trigger evaluation.
ohlcv_cache_YYYY-MM-DD.json
Daily Yahoo fetch cache. Written by Aurelius sonar. Read by Bridge, Walk, Future, Render, Observer, Sim. Prevents redundant network calls.
backtest_cache.json
7-day backtest result cache. Written by Aurelius and Witness. Read by Walk and Aurelius. Prevents redundant computation.
analyst_cache.json
7-day analyst rating cache. Written by Aurelius. Prevents repeated Yahoo crumb+quoteSummary fetches.
ladder_watch.json
Active position coordinates under Observer monitoring. Written by Observer. Read by Sim and Render.
forecast_clearance_YYYY-MM-DD.json
TF1 clearance results per ticker. Written by Future. Read by Witness for future_perf audit.

How to Patch Safely

Rule 1: Always patch from the uploaded source file, never from a prior output. The uploaded file is ground truth.
Rule 2: Read the chamber meta note before writing any code. Understand what the chamber decided before changing it.
Rule 3: Deliver patches as chamber snippets, not full file rewrites. This preserves the surrounding architecture.
Rule 4: Two failed patches means stop and diagnose — do not keep patching. Read the self-terminal debug output.
Rule 5: Check the dependency map before modifying any chamber. Changing a constant in Chamber 1 affects Bridge, Sim, Walk, and Render simultaneously.
Rule 6: Never write business logic into Chamber 0 or Chamber 14. Chamber 0 is imports only. Chamber 14 is the entry point only.
Rule 7: If a patch requires modifying the same data structure in two different nodes, stop and ask whether the architecture has a design decision to make first.

Naming Conventions

Names in this codebase carry semantic meaning beyond their function. They are a compressed vocabulary. Do not rename them to conventional technical names — the vocabulary is load-bearing.

soul_state — Not a status flag. The accumulated classification of a ticker's signal history. GHOUL means degraded. ORACLE_NAMED means verified.
SHATTER — Not a stop loss. A geometrically calculated floor derived from ATR and entry price — the coordinate where the geometry fails.
960 Seal — Not a score ceiling. A named entry state — a coordinate that has passed every gate simultaneously. Verified from Chamber 7 header and KP scoring logic.
RECLAMATION — Not a buy signal. A specific signal type meaning price has returned to a previously established ladder level.
geo_trajectory — Not a trend indicator. The accumulated directional history of a ticker's position within its geometric structure.

What Not To Do

✗ Do not add a new JSON file without checking if an existing file serves the same purpose
✗ Do not write cache logic inside worker threads — workers read from memory only, writes happen after all workers complete
✗ Do not coerce None values to defaults inside indicator functions — None means insufficient data, not zero
✗ Do not skip reading the meta note and go straight to the code
✗ Do not modify Chamber 1 constants without tracing all downstream nodes that read them
✗ Do not run nodes out of pipeline order — downstream nodes depend on upstream outputs
✗ Do not add unbounded lists or logs — every accumulating structure needs a cap or rotation
